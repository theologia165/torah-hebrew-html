# 朝一トーラー 音声品質管理部

音声の障害受付、過去事例照合、検品、修正、再検品、既存ページへの差し替え、完了証明をこの部署に集約する。別サービスや常駐エージェントは設けず、Workが内容の判断を、Actionsが変換・機械検査・配信を担当する。

## 正本と入口

- 障害・修正台帳：[incidents.json](incidents.json)。過去の説明、実装済み修正、今回確認できた事実、未検証事項を区別する。
- 運用仕様：[audio-quality.md](../../spec/audio-quality.md)。担当者は音声問題の都度、この一つの仕様へ入る。
- 統一コマンド：`python ver3/scripts/audio_quality.py`。
- 当該RUNの検品結果：`audio-quality.json`。音源・本文・MP3・検品記録のhashで対象を固定する。
- 内容検品：`audio-content-review.json`。機械処理が合格印を代筆しない。
- 修復履歴：`audio-repairs/{repair_id}/`。候補、旧音声、検品、差し替え前後の配信証明を残す。

## 担当範囲

| 段階 | 担当と成果物 |
|---|---|
| 受付 | Workが症状・NNN・対象節・発生位置を記録。台帳へ新規登録し、確定原因と推定原因を分ける |
| 機械検品 | Actionsが既存verify_audio、当該RUN本文対応、既知障害照合を実行。正常媒体と不良媒体を分ける |
| 内容検品 | Work／聴取者が全節の冒頭語・末尾語・語順・他節混入・途中切断・速度を確認。方法と根拠を記録 |
| 修正 | 音源アダプタ／共有処理を修正。過去事例の回帰テストを実行。台帳の実装状態を更新 |
| 再検品 | 公開前の候補MP3を別置きし、機械検査と全節の内容検品をやり直す。旧音声の検品は流用しない |
| 差し替え | 合格候補だけを同じNotionページへ配信。ページ・公開音声バイト列を再取得照合 |
| 終了 | `closed.json`へrequest・入力・音声・内容検品・配信証明のhashを記録。実装完了と音声修復完了を混同しない |

## 品質状態

`PASS`は機械検査と全節の内容検品がともに合格した場合だけ。`CONTENT_REVIEW_PENDING`は機械検査のみ合格、`BLOCKED`は既知障害・機械不合格・内容不合格・未実装節がある状態。配信側の`delivery.json=PASS`は配信の整合であり、音声品質PASSの代用にはしない。

通常生成は毎回この部署の報告を作る。証明された不良音声はmanifestから隔離し、正常な本文・HTML・画像・他節音声は既存のPARTIAL方針で継続する。内容未検品と不良確定も区別する。従来の本番番号の進行条件は別契約であり、この導入だけで既完了RUNの番号やページを変更しない。

085は最初の未解決案件として登録した。本部署の設置によって085の音声が修正されたとは扱わない。先頭0のあるラベル形式を全音源へ一律適用せず、当該音源とラベルに根拠を持つ対応修正が必要である。

## 回帰検査

```sh
python ver3/scripts/test_audio_quality.py
python ver3/scripts/test_audio_primary_module.py
python ver3/scripts/test_audio_fallback_policy.py
python ver3/scripts/test_handoff_contract.py
```

027の工程抜け、041の物理欠損と代替制限、047の加速禁止、048の無音境界補正、085の既知ラベル誤対応、検品後の音声変更、別RUNの検品流用、未聴取PASS、修復候補の公開前保留を検査する。081のJSON2形式不一致は音声生成以前の障害として範囲外へ記録する。新しい障害は「症状・原因・証拠・実装修正・回帰検査・残作業」を揃えて追記する。
